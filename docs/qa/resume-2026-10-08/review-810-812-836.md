## Actionable Finding: TEST Reseeding Leaves Unified References Stale

**P2 — `migrations/008_populate_mock_database.py:235-236,439-451`.**
`seed_test_provider_database` permits reseeding an existing non-story database.
Its `populate_post_transition_data` truncates `layers` and `characters` with
`CASCADE`. On a populated post-148 target, this removes every authoritative
junction row without firing migration 148's row mirror or subtype-forget triggers.
The new unified table survives, so the seeder commits stale character, faction
and place references. Fresh fixture clones happen to start with none and do not
expose this path.

Read-only catalog evidence: connected to `NEXUS_template` with
`default_transaction_read_only=on` from connection startup, asserted
`SHOW transaction_read_only = on`, read `max(schema_migrations.version) = 145`,
and traversed every `pg_constraint` foreign-key edge from referenced table to
referencing table (TRUNCATE CASCADE follows all such edges regardless of their
ON DELETE action). No row reads or writes were needed.

| Root | FK Cascade Closure | Reaches `narrative_chunks` | Reaches `entities` |
| --- | ---: | --- | --- |
| `public.layers` | 32 tables | No | No |
| `public.characters` | 9 tables | No | No |

The layers closure reaches **all three** authoritative junctions:

- `layers → zones` (`zones_layer_fkey`) → `places` (`places_zone_fkey`) →
  `place_chunk_references` (`place_chunk_references_place_id_fkey`).
- `places → characters` (`fk_characters_current_location`) →
  `chunk_character_references` (`chunk_character_references_character_id_fkey`).
- `places → factions` (`factions_primary_location_fkey`) →
  `chunk_faction_references` (`chunk_faction_references_faction_id_fkey`).

Migration 146 only adds `story_identity → story_lineage`, and migration 147 adds
no foreign key. Migration 148's new table references only `narrative_chunks`
and `entities` (`migrations/148_chunk_entity_references.sql:105-109`), so adding
146-148 cannot make it part of the truncation closure. Its triggers at lines
143-154 and 287-297 are row DELETE / INSERT-UPDATE-DELETE triggers, not TRUNCATE
triggers. The comments claiming no current truncation path therefore need this
seeder exception noted.

Minimal 816-owned fix: immediately before the truncates, check
`to_regclass('public.chunk_entity_references')`; when present, delete its rows
inside the existing transaction. A conditional is needed while provider
databases can predate migration 148. Clearing all three kinds is correct here:
all three authoritative junctions are truncated, including the faction junction.
No generic TRUNCATE trigger is needed.

Combined regression after gate coordination: on a disposable post-148 database,
seed one chunk with character, faction and place references through the ordinary
junction writer, assert normalized parity, invoke the real TEST seeder again,
and assert all three junctions and unified rows are empty while the retained
chunk remains. Exercise rollback through the existing one-transaction seeder
contract. Keep this regression on integration or a branch containing both 816
and 836; standalone 816 currently lacks migration 148. No test has been run for
this finding yet.
